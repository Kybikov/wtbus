# Перевірка сесії

- `proxy.ts` перевіряє сесію через внутрішній `/api/v1/auth/me` перед відкриттям захищеної сторінки. Самої наявності cookie недостатньо.
- Відсутня, прострочена або відкликана сесія веде на `/login?next=...`; недійсна cookie очищається. Після входу відновлюється локальна адреса з параметрами. Зовнішні адреси в `next` відхиляються.
- Серверна перевірка має таймаут 5 секунд. Якщо сервіс недоступний, сторінка повертає `503` зі вказівкою повторити спробу. Cookie залишається: збій інфраструктури не є виходом з акаунта.
- Захищені сторінки та відповіді перевірки сесії не кешуються спільними кешами. Авторизацію кожного запиту до даних додатково перевіряє Go API.
- Для запитів браузера до захищених API використовуйте `sessionFetch` з `lib/session-navigation.ts`. Він обробляє `401` переходом на вхід, зберігаючи оригінальну відповідь для викликача. `403`, `429`, мережеві помилки й `5xx` не спричиняють цей перехід. Запити входу, вибору компанії та виходу виключені.
- `SessionMonitor` перевіряє сесію при навігації, поверненні до вкладки, відновленні мережі та щохвилини у видимій вкладці. Офлайн-помилки не завершують сесію та не видаляють чергу GPS.
- Вихід очищає HttpOnly cookie навіть при недоступності API; повна навігація на вхід скидає попередній стан сторінки. Якщо API недоступний, серверне відкликання токена не гарантується, але браузер припиняє ним користуватися.

## Особистий профіль

`/profile` відкривається з меню аватара та показує ім’я, email і роль поточної сесії. Ім’я змінюється через `PATCH /api/v1/auth/me`; довільні ID, email і роль у запиті заборонені. Email залишається незмінним і використовується для входу.

Зміна пароля потребує поточного пароля, мінімум 10 символів і максимум 72 байти (обмеження bcrypt). Оновлення пароля та відкликання інших сесій цього користувача відбуваються в одній транзакції. Поточна сесія зберігається. Системний аккаунт редагувати не можна.

## Перевірки

`TestProfileValidation` перевіряє формат імені та обмеження bcrypt, а `TestProfilePostgres` — збереження імені, заборону зміни ролі/чужого ID, транзакційний rollback, зміну пароля, відкликання інших сесій і обмеження кількості спроб. Для інтеграційного тесту використовуйте лише окремі тимчасові PostgreSQL/Redis через `PROFILE_TEST_DATABASE_URL` та `PROFILE_TEST_REDIS_URL`.

`npm test` перевіряє безпечне повернення після входу, різницю між `401` і збоями сервера, єдиний перехід при паралельних помилках та збереження відповіді GPS. `go test ./...` перевіряє `401` для відсутньої сесії та `503` при недоступності бази.

Під час ручної перевірки production-збірки перевірте відкриття сторінки без cookie, недійсну й відкликану сесію, вхід із поверненням на початкову адресу, втрату сесії у відкритій вкладці, вихід та недоступність API. `/login`, PWA-ресурси й автономний екран мають залишатися доступними без сесії.
