# Історія дій та діагностика

У налаштуваннях компанії `/settings/activity` власник, адміністратор та розробник бачать журнал дій. Вкладка запитів API доступна лише власнику та розробнику. Картки записів показують останні 30 подій; загальний журнал підвантажує по 50 за незмінним ID без зміщення сторінок. Старі події не вигадуються і не заповнюються заднім числом.

## Що фіксується

Після успішних авторизованих змін API записує компанію, співробітника, дію, колекцію, ID запису, час та ідентифікатор запиту. Для основних змін записів порівнюються стан до та після запиту; зберігаються лише назви фактично змінених полів. Для створення і налаштувань зберігаються лише назви відомих переданих полів. Значення полів, тіла запитів/відповідей, заголовки, токени, паролі, IP і параметри пошуку в журнали не потрапляють. Невдала спроба залишається в журналі запитів і не видається за успішну зміну.

Запити API мають метод, шаблон адреси, HTTP-результат, тривалість, автора та згенерований request ID. Вимірюється обробка запиту API, без мережевого часу браузера та подальшого збереження аудиту. Неавторизовані та публічні запити доступні лише у структурованих серверних логах, без прив'язки до компанії. Проби здоров'я і довге WebSocket-з'єднання не журналюються як звичайні API-запити. Запити зберігаються 30 днів; очищення обмежено 5000 рядками за хвилину. Історія ділових дій не видаляється автоматично. JSON-логи API обмежені ротацією 5 × 10 MB.

Аудит HTTP зберігається окремою короткою транзакцією після обробки запиту і має 2-секундний ліміт. Це не транзакційний журнал усіх SQL-змін: при аварійному завершенні процесу між зміною і записом аудиту можливий пропуск. При помилці збереження залишається структурований лог з request ID, компанією й автором; успішну операцію не повторюємо, щоб не дублювати платежі або бронювання. Прямі SQL-правки поза API не отримують вигаданого автора. Зберігаються вже наявні транзакційні події бота про доставку повідомлень, звірку оплати та завершення строку бронювання; зразки GPS і фонове обслуговування пристрою не засмічують журнал менеджера.

## Реальний час

Існуюча черга PostgreSQL → Redis → WebSocket передає тільки повідомлення інвалідації. Додано інвалідації інтеграцій та курсів. Історія в деталях оновлюється окремо від полів форми, тому набраний текст не замінюється. Перепідключення та повернення у вкладку оновлюють відображення. Перевірки інтеграцій виконуються незалежним робітником, максимум 4 підключення за цикл, кожне не частіше п'яти хвилин; новий ключ чекає найближчого циклу. Кожний запит обмежений шістьма секундами, цикл — двадцятьма. Загальна з ручною перевіркою Redis-пауза захищає Monobank від повторних викликів частіше хвилини. HTTP 429 не перетворюється на помилку ключа.

Результат перевірки зберігається з відбитком поточного ключа. Заміна ключа скидає старе здоров'я; запізніла відповідь для попереднього ключа не може позначити новий робочим. `Не подключено` означає відсутність ключа, `Ожидает проверки` — ще немає результату, `Работает` / `Ошибка` — останню завершену перевірку. Час біля бейджа — остання успішна перевірка API, а не підтвердження останнього платежу. Зміна стану інтеграції окремо журналюється як автоматизація.

Перед розгортанням: резервна копія та перевірка відновлення, міграція 42. Вона додає таблиці журналу запитів та здоров'я підключень, індекси, інвалідації та скидання стану після заміни ключів. Відкат видаляє нові діагностичні дані і припустимий лише після збереження потрібної історії та відкату коду.

Перевірки: `npm test`, typecheck, lint, production build, `go test ./...`, `go vet ./...`. З ізольованою PostgreSQL у `NOTIFICATION_TEST_DATABASE_URL`: TestActivityPostgres, TestSettingsPostgres, TestNotificationDeliveryPostgres. Тести не надсилають реальні повідомлення і використовують підмінені провайдери.
