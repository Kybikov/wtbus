# Публічне бронювання

Пасажирська сторінка Vivat: `/book` → `/book/vivat-bus`. Для іншого перевізника: `/book/{tenant-slug}`. Посилання доступне команді в меню профілю — «Страница бронирования». Реєстрація пасажира не потрібна; доступ до CRM залишається захищеним.

Інтерфейс використовує встановлені ліцензійні React Bits Pro `filtering-8` та `wizard-2`, адаптовані під Vivat і shadcn/ui. Демонстраційні авіарейси, ціни та авіакомпанії вилучені.

Міста завантажуються з активних маршрутів БД і доступних регулярних рейсів без прив’язаного маршруту. Місто прибуття залежить від міста відправлення. Пошук виконується на сервері за конкретною датою в часовому поясі перевізника та кількістю пасажирів. Продаються тільки майбутні регулярні рейси `new`/`assigned` з тарифом за пасажира, без перекриття недоступністю, із діючими маршрутом і автомобілем та достатньою кількістю місць. Немає розкладу на обрану дату — немає вигаданих результатів.

Оформлення: контакт відповідального пасажира, дата народження, обов’язкові додаткові поля бронювання з БД, перевірка даних і згода на обробку для поїздки. Результат — бронювання `cash_on_boarding`, джерело `web` («Сайт» в CRM). IBAN не потрібен; банківська онлайн-оплата на цій сторінці поки не пропонується. Існуючий процес водія та фінансів обробляє таке бронювання як інші готівкові бронювання.

Ціна визначається сервером; зміна ціни після пошуку потребує нового вибору рейсу. Місця резервуються в транзакції з блокуванням рейсу. `requestKey` забезпечує ідемпотентність повтору після втраченої відповіді; змінений запит із тим самим ключем відхиляється. На один телефон не створюються дублікати активного бронювання на той самий рейс. Наявний клієнт за телефоном повторно використовується без перезапису його імені. Номер підтвердження не відкриває публічного доступу до приватних даних чи керування бронюванням.

API: `GET /api/v1/public/{slug}/catalog`, `GET .../trips`, `POST .../bookings`. Веб BFF дозволяє тільки ці дії, не передає сесію співробітника й відхиляє міжсайтові POST. Розмір тіла обмежений 16 КіБ. Redis обмежує спроби оформлення: 10 на телефон і 200 на перевізника за 15 хвилин. Якщо Redis недоступний, нові бронювання тимчасово не приймаються. Це базовий захист; при масштабуванні публічного трафіку додати захист від ботів на рівні проксі.

Створення фіксується в `activity_events` від системного користувача «Автомат», дія `public_booking_created`, без контактів пасажира в події.

## Розгортання та перевірка

Дати в пошуку й оформленні вибираються через локалізований shadcn Calendar у Popover; місяць і рік також використовують shadcn Select. Минулі дати поїздки та майбутні дати народження недоступні.

Розпродані рейси на обрану дату залишаються у результатах із нулем вільних місць і вимкненим бронюванням. Недостатня кількість місць для групи позначається окремо. Якщо немає жодного рейсу з достатньою кількістю місць, API повертає до трьох найближчих доступних відправлень до та після обраної дати. Застосовуються ті самі правила продажу, напрямок і кількість пасажирів; рейси, що вже відправилися, не пропонуються. Варіант можна одразу обрати для оформлення.

Перед запуском нового API застосувати міграцію `000027_public_booking` після резервного копіювання та перевірки відновлення в окремій БД. Старий API сумісний із розширеним переліком джерел.

Перевірки: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `go test ./...`, `go vet ./...`.

Інтеграційний тест запускається **тільки в одноразових, мігрованих PostgreSQL і Redis**:

```sh
PUBLIC_TEST_DATABASE_URL=postgres://... PUBLIC_TEST_REDIS_URL=redis://... go test ./cmd/api -run TestPublicBookingPostgres -v
```

Він перевіряє анонімний пошук, мінімальні публічні відповіді, валідацію, ціну, готівку без IBAN, ідемпотентність, дублікати, статистику системного користувача, паралельний продаж останнього місця й блокування продажів.
